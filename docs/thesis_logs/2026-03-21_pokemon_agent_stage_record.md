## 阶段摘要（可直接写入论文）

本阶段工作的核心目标是提升宝可梦自动游玩 Agent 在游戏开局阶段的稳定性，并验证“仅依赖大模型视觉理解截图、将 RAM 作为辅助状态”的方案是否优于此前的本地 CV 启发式流程。围绕这一目标，系统重点修复了开场剧情脚本与地图探索记忆之间的耦合错误、RAM UI 标志与真实游戏画面不同步的问题，以及早期开局阶段若干会导致死循环的执行器逻辑。

实验结果表明，在加入回合上限控制、开场脚本锁存、模型侧 `SCREEN_TYPE` 回传、命名界面确定性操作和若干窄状态 bootstrap 宏后，Agent 已经能够在 `1000` 回合预算内稳定通过开场、离开家门、完成 Pallet Town 段落并推进到大木博士研究所的 starter 选择提示阶段。当前系统的主要瓶颈已经从“开局即卡死”转移为“研究所内领取 starter 阶段缺少专项状态机”，说明问题重心更多位于交互控制逻辑，而不是简单的提示词能力不足。

## 阶段背景

本项目的目标是让大模型驱动的智能体自主游玩《Pokemon Red》。前期测试表明，Agent 的主要问题不在单一提示词，而在于“提示词、RAM 状态解释、启动剧情脚本、UI 判定、动作执行器”之间存在耦合错误，导致模型虽然能看到截图，但常常在错误的时机做出错误动作，或者被错误的 RAM 标志持续误导。

本阶段的改进参考了以下两类材料：

- 用户提供的 `Gemini Plays Pokemon` 公开说明，用于借鉴其“截图 + 游戏状态 + 专项代理 + 长程运行”的设计思想。
- 用户提供的论文 `c:\Users\cfn03\Downloads\gemini_v2_5_report.pdf`，用于理解高性能 LLM Agent 在复杂序列任务中的支架思路。

## 本阶段的主要工作

### 1. 保持“原始截图 + 大模型视觉”路线

本阶段继续保留此前已经完成的架构方向：

- 关闭 harness 侧本地像素级视觉分类器。
- 让模型直接读取原始截图。
- RAM 数据只作为辅助状态，而不再承担最终 UI 语义判定。

这一方向的原因是：

- 本地 CV 启发式规则在黑边、文字框、开场转场、房间裁切等情形下误判率较高。
- 大模型对截图中的语义理解能力更强，尤其适合处理开场对白、命名界面、研究所对白等复杂 UI。

### 2. 增加测试回合上限

为满足实验要求，本阶段在系统中增加了硬性测试上限：

- 在 `config.yaml` 中加入 `testing.max_turns: 1000`
- 在主循环中加入上限判断，到达 `1000` 回合后自动停止并保存检查点

这样可以保证后续所有实验都可控、可复现、可比较。

### 3. 修复开场脚本导致的地图记忆污染

在开场阶段，游戏 RAM 已经可能出现“看起来像在某个地图坐标上”，但实际上玩家尚未真正获得自由移动控制权。如果此时把坐标直接写入探索记忆，就会导致：

- 房间探索状态被错误初始化
- 导航器把开场脚本当作正常地图
- 后续路径规划建立在错误世界模型之上

本阶段延续并强化了“开场脚本锁存（latch）”思路：

- 在真正检测到自由移动前，禁用地图探索与导航记忆更新
- 把命名界面、开场对白、过场动画等都视为 `pre_starter_script`

### 4. 增加模型侧 SCREEN_TYPE 参与 UI 判定

为了减少单纯依赖 RAM 的误判，本阶段让主模型在每次决策时额外输出：

- `SCREEN_TYPE`

然后主循环会用该字段对 RAM 推断的 UI 阶段进行修正。这样做的效果是：

- 标题页、主菜单、命名页、对白、过场动画等可由模型直接报告
- 当 RAM 的 `text_box_active` 与截图内容冲突时，系统不再完全相信 RAM

### 5. 修复命名界面和启动界面的自动操作逻辑

本阶段对以下已知界面加入了确定性处理：

- `title`
- `startup_menu`
- `options_menu`
- `naming_screen`

其中命名界面从原先较不稳定的操作方式，调整为更保守的：

- 先输入一个字母
- 再用 `start` 确认

这使得命名流程在 API 抖动存在时依然可以稳定推进。

### 6. 修复 Pallet Town 开场前的假对话锁死

这是本阶段最重要的早期修复之一。

#### 发现的问题

在前序长时间测试中，Agent 曾稳定卡死在：

- `Map ID: 0`
- `Coordinates: (12, 2)`

当时的截图显示角色已经站在 Pallet Town 室外，但 RAM 仍持续报告：

- `text_box_active = True`

于是系统把该状态解释成“对白中”，主循环长期执行：

- `wait`
- `a`
- `wait`
- `a`

形成无限循环。

#### 离线分析结论

通过读取检查点 `checkpoint_1300` 并离线回放，发现：

- 这并非完全死机，角色仍可通过某些按键序列发生横向位移
- `start + a` 或 `start + b` 可以清掉假的 `text_box_active`
- `left, left, a` / `right, right, a` 可以把角色推进到相邻位置

因此，这个问题不是“模型不会玩”，而是“RAM UI 标志错误 + 执行器逻辑被锁死”。

#### 本阶段解决方法

本阶段在这一点上做了两类修复：

- 对 `map 0, y = 2, x in [10, 14]` 的已知状态加入“假对白”窄特判
- 增加一个专门的 bootstrap 宏，把角色从 Pallet Town 北口假锁死位置重新桥接回 Oak 触发点

### 7. 修复卧室开场 bootstrap 触发条件过窄的问题

第一轮修复之后，新的测试又发现一个问题：

- 卧室起始点 `map 38, (3,6)` 的脱困宏原先只在 `screen_type == dialogue` 时触发
- 但在 API 不稳定或模型输出异常时，这一状态可能会被推断为 `indoor`
- 结果 deterministic 宏没有接管，系统又回到了原地反复按键

因此本阶段把卧室 bootstrap 的触发条件放宽为：

- 只要处于 `map 38, x = 3, y = 6`，即可直接接管

这个修改显著提升了开场稳定性。

### 8. 增加中文响应下的 SCREEN_TYPE fallback 推断

测试中发现，模型并不总是严格按英文格式输出：

- 有时输出中文自然语言
- 有时输出 JSON 片段
- 有时只在推理中描述“这是命名界面/对话/开场剧情”

原来的 `_infer_screen_type_from_text()` 主要匹配英文关键词，因此：

- 模型虽然“理解对了”
- 主循环却“接收不到”

本阶段补充了中文关键词，如：

- 命名 / 起名 / 名字
- 对话 / 对话框 / 台词
- 开场 / 序章 / 剧情 / 大木博士
- 菜单 / 标题画面 / 新游戏 等

该修改提高了模型输出格式不稳定时的容错率。

## 当前阶段的主要困难

### 1. API 提供方稳定性不足

本阶段多次出现接口异常，例如：

- `token_invalidated`
- `token_revoked`
- 上层表现为 HTTP `500`，但实际包裹的是提供方侧 `401`

这会带来两个问题：

- 主模型输出中断，系统退回保守动作
- `SCREEN_TYPE` 无法稳定提供，导致 UI 判定精度下降

### 2. RAM UI 标志与真实画面不同步

这是本项目的核心工程难点之一。

典型表现：

- 截图中没有对白框，但 RAM 仍显示 `text_box_active = True`
- 截图中已经进入“可尝试移动”窗口，但系统仍把它解释为 dialogue
- 行动执行器会因为 `text_box_active` 而提前停止移动重试

这说明不能仅依赖 RAM 判断 UI 阶段，必须引入：

- 截图语义理解
- 位置上下文
- 专项状态机

### 3. 研究所 starter 选择阶段仍缺少专门控制器

当前系统已经能稳定到达：

- 研究所
- starter 选择提示

但仍未可靠完成“真正选择精灵球并拿到 starter”。离线分析表明：

- 该阶段不是完全死锁
- 对话框会在截图层面出现“显示 / 隐藏”切换
- 但 RAM 的 `text_box_active` 长时间保持为 `True`
- 系统因此把短暂的可移动窗口浪费掉了

也就是说，当前最需要的不是更大的提示词，而是：

- 一个研究所 starter 阶段的专项控制策略

### 4. 模型输出格式并不稳定

虽然系统要求模型输出：

- `SCREEN_TYPE`
- `REASONING`
- `ACTION`
- `GOAL_UPDATE`

但实际响应中常出现：

- 中文自由文本
- JSON 片段
- 只有行动，没有完整字段

这要求解析层具备更强容错性。

## 当前代码层面的有效成果

本阶段验证为“有效且保留”的改动包括：

- 主循环硬性 `1000` 回合停止
- 开场地图记忆锁存
- 模型 `SCREEN_TYPE` 接入主循环
- 命名界面自动确认
- 卧室 bootstrap 放宽触发
- Pallet Town 北口假对白锁死修复
- 中文 SCREEN_TYPE fallback 推断

## 当前阶段结论

本阶段尚未达到“真正完整游玩”的目标，但已经完成了从“开场早期即失效”到“1000 回合内稳定推进至研究所 starter 选择提示”的关键跃迁。

因此，从论文写作角度，可以将本阶段的结论表述为：

> 通过引入开场脚本状态锁存、模型侧 UI 类型回传、早期关键节点的确定性 bootstrap 宏、以及对错误 RAM UI 标志的局部纠偏，系统成功突破了早期开局与 Pallet Town 室外假对白死锁问题，使 Agent 能够在 1000 回合预算内稳定推进到大木博士研究所 starter 选择阶段。当前剩余瓶颈主要集中在研究所内 starter 领取流程的专门状态机缺失，而非通用提示词能力不足。
